### 9.14.1 模块概述

[`CarDucking`](packages/services/Car/service/src/com/android/car/audio/CarDucking.java)（`final class CarDucking implements CarZonesAudioFocus.CarFocusCallback`，:38）实现AAOS系统级Ducking：Per-Zone 焦点持有者变化后，按 [`CarDuckingUtils`](packages/services/Car/service/src/com/android/car/audio/CarDuckingUtils.java) 的静态策略表（`sContextsToDuck` :45，完整矩阵见 [9.6](09_9.6_CarAudioContext-车载音频上下文深度解析.md)）计算该 Zone 需要 Duck/取消 Duck 的设备地址，生成 `CarDuckingInfo` 并经 `AudioControlWrapper.onDevicesToDuckChange()` 通知HAL，由DSP执行增益调整（HAL 侧链路见 [10.4](../10_AudioControl_HAL/10_10.4_Ducking机制.md)）。

**与Android原生Ducking不同**：CarDucking不经App层——被duck的App不会收到 `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK`，粒度为**设备地址级**、按Zone独立计算。

**核心职责（12L 实况）：**
- 实现 `CarZonesAudioFocus.CarFocusCallback`，接收 Per-Zone 焦点持有者集合变化
- 为每个Zone维护当前 `CarDuckingInfo`（`mCurrentDuckingInfo`，:44），供差集计算（unduck）
- 委托 `CarDuckingUtils` 完成 usage→context→duck判定→地址 换算
- 汇总各区新 `CarDuckingInfo` 后一次性下发 HAL

### 9.14.3 焦点变化处理 — onFocusChange（:65-77）

真实签名为 **批量** 回调：`CarZonesAudioFocus` 结算完各Zone焦点后，把发生变化的 zoneId 数组与全部焦点持有者一并传出，`CarDucking` 循环逐区更新并**一次性**下发：

```java
// CarDucking.java:65-77（逐字摘录）
public void onFocusChange(int[] audioZoneIds,
        @NonNull SparseArray<List<AudioFocusInfo>> focusHoldersByZoneId) {
    synchronized (mLock) {
        List<CarDuckingInfo> newDuckingInfos = new ArrayList<>(audioZoneIds.length);
        for (int i = 0; i < audioZoneIds.length; i++) {
            int zoneId = audioZoneIds[i];
            List<AudioFocusInfo> focusHolders = focusHoldersByZoneId.get(zoneId);
            CarDuckingInfo newDuckingInfo = updateDuckingForZoneIdLocked(zoneId, focusHolders);
            newDuckingInfos.add(newDuckingInfo);
        }
        mAudioControlWrapper.onDevicesToDuckChange(newDuckingInfos);
    }
}
```

### 9.14.4 Ducking更新 — updateDuckingForZoneIdLocked（:80-88）

```java
// CarDucking.java:80-88（逐字摘录）
@GuardedBy("mLock")
private CarDuckingInfo updateDuckingForZoneIdLocked(int zoneId,
        List<AudioFocusInfo> focusHolders) {
    CarDuckingInfo oldDuckingInfo = mCurrentDuckingInfo.get(zoneId);
    CarDuckingInfo newDuckingInfo = generateNewDuckingInfoLocked(oldDuckingInfo,
            focusHolders);
    mCurrentDuckingInfo.put(zoneId, newDuckingInfo);
    return newDuckingInfo;
}
```

**旧值的作用**：`generateNewDuckingInfoLocked` 只算出新的 `addressesToDuck`；`addressesToUnduck`（取消Duck）= 旧 `mAddressesToDuck` − 新 `addressesToDuck` 的差集，因此 `mCurrentDuckingInfo` 必须随每次更新覆盖保存。

### 9.14.5 Ducking计算 — generateNewDuckingInfoLocked（:102-113）

计算全部委托 `CarDuckingUtils`（三步）：

```java
// CarDucking.java:102-113（逐字摘录）
@GuardedBy("mLock")
private CarDuckingInfo generateNewDuckingInfoLocked(CarDuckingInfo oldDuckingInfo,
        List<AudioFocusInfo> focusHolders) {
    int zoneId = oldDuckingInfo.mZoneId;
    CarAudioZone zone = mCarAudioZones.get(zoneId);

    int[] usagesHoldingFocus = CarDuckingUtils.getUsagesHoldingFocus(focusHolders);
    List<String> addressesToDuck = CarDuckingUtils.getAddressesToDuck(usagesHoldingFocus, zone);
    List<String> addressesToUnduck = CarDuckingUtils.getAddressesToUnduck(addressesToDuck,
            oldDuckingInfo.mAddressesToDuck);

    return new CarDuckingInfo(zoneId, addressesToDuck, addressesToUnduck, usagesHoldingFocus);
}
```

三步换算（`CarDuckingUtils` 内部，逐字源码见 [10.4.3](../10_AudioControl_HAL/10_10.4_Ducking机制.md)）：

| 步骤 | 方法（真实行号） | 语义 |
|------|-----------------|------|
| ① 提取usage | `getUsagesHoldingFocus` :112 | 遍历 `focusHolders` 收集 `getSystemUsage()` 去重 |
| ② duck判定 | `getAddressesToDuck` :127 | usage→context→对每个持有者context查 `sContextsToDuck` 行取并集→映射到设备地址→**排除仍持有焦点（未被duck）的context的地址** |
| ③ unduck差集 | `getAddressesToUnduck` :141 | 旧duck地址 − 新duck地址 |

**关键设计**（`CarDuckingUtils.java:138` 注释，逐字）：同一设备可能被多个Context映射——若其中一个Context仍在持有焦点且未被duck，该设备不应被duck。

### 9.14.8 与Android原生Ducking的区别

| 特性 | Android原生Ducking | AAOS CarDucking |
|------|-------------------|-----------------|
| 执行位置 | App自行降低音量 | DSP硬件层(HAL通知) |
| 粒度 | App/Player级 | 设备地址级别 |
| Zone感知 | 无 | Per-Zone独立计算 |
| 通知方式 | App收到AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK | HAL收到onDevicesToDuckChange（App无感知） |
| 增益控制 | App自行决定衰减量 | DSP完全自定义衰减量 |
| 适用场景 | 手机/平板 | 车载多Zone系统 |

### 9.14.9 典型场景：导航播报Ducking音乐

12L 真实机制（无 Hold/Lose 列表，全部由持有者集合+静态表推导）：

```
前提（FocusInteraction 交互矩阵，MUSIC 为持有者行）:
  MUSIC(持有) × NAVIGATION(请求) = CONCURRENT → 导航与音乐并存，两者都在 focusHolders

① getUsagesHoldingFocus → usages = {USAGE_MEDIA, USAGE_ASSISTANCE_NAVIGATION_GUIDANCE}
② usage→context: {MUSIC, NAVIGATION}
③ 逐持有者context查 sContextsToDuck 行:
     sContextsToDuck[NAVIGATION] = {MUSIC, CALL_RING, CALL, ALARM, NOTIFICATION,
                                    SYSTEM_SOUND, VEHICLE_STATUS, ANNOUNCEMENT}
     sContextsToDuck[MUSIC]      = {}（空）
   → contextsToDuck = {MUSIC, CALL_RING, CALL, ...}
④ unduckedContexts = 持有者context − ducked = {NAVIGATION}
⑤ addressesToDuck = ducked contexts 的设备地址 − undocked context(NAVIGATION) 的设备地址
   → MEDIA VolumeGroup 的 bus0_media_out 被duck（除非同设备还承载导航）
⑥ addressesToUnduck = 上次duck地址 − 本次duck地址
```

导航播报结束（NAVIGATION abandon）→ 持有者只剩 MUSIC → contextsToDuck 为空 → 差集把 bus0_media_out 放入 `addressesToUnduck`，DSP恢复增益。

**注意**：duck判定是"每个持有焦点的高优先级context会让静态表列出的context组被压低"，与"谁先来谁后被duck"无关；被duck的context若同时自己持有焦点且不在任何duck行内，其设备被排除（步骤④⑤）。
