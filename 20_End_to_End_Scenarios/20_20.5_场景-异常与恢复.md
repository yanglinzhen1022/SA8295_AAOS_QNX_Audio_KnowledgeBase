## 2. audioserver / CarAudioService 崩溃与重启

- `audioserver` 死亡后由 init 重启（标准 Android 行为）；重启后 AudioFlinger/AudioPolicyManager 重建，**已注册的 AudioPolicyMix 不会自动恢复**——树内 CarAudioService 仅在 init 时 `registerAudioPolicy`（`CarAudioService.java:631`），car/audio 目录未见对 audioserver 的死亡监听（`linkToDeath/serviceDied` 仅 AudioControlWrapper 系）；因此需要重启 `com.android.car` 让 CarAudioService 重新注册（命令见下条，[11.7 故障排查](../11_Vendor_Layer/11_11.7_OEM定制指南.md)）——**重建不是无缝回放**（[5.9 §7.2](../05_AudioFlinger/05_5.9_音乐播放全栈调用链.md) 的客户端侧恢复语义）；
- CarAudioService 重建时重新解析 `car_audio_configuration.xml` 并重建 Zone/动态路由（[9.2 CarAudioService](../09_AAOS_Car_Audio/09_9.2_CarAudioService-车载音频核心服务.md)、[9.11 动态路由](../09_AAOS_Car_Audio/09_9.11_CarAudioDynamicRouting-动态路由构建.md)）；
- 重启 CarAudioService 的手动入口：`adb shell am force-stop com.android.car`（[11.7 故障排查](../11_Vendor_Layer/11_11.7_OEM定制指南.md) 已核验的命令形态）。

## 3. ADSP SSR（子系统重启）——跨 VM 的两层清理

这是本场景最重要的**双域**知识点：ADSP 重启对 Android 与 QNX 两侧各有清理路径，且**不能画成一张图**：

| 侧 | 行为 | 讲解 |
|---|---|---|
| QNX gsl_be | HAB recv 返回 `-ENODEV` → session cleanup（数据库、图、OOB 队列）→ 销毁连接与 session；`reset_only` 分支区分"仅清图记录"与"调用本地 gsl_close()" | [18.2 §清理](../18_AGM_GSL_Architecture/18_18.2_GSL跨VM控制与缓冲区.md) |
| Android 内核 | `q6_notifier`/SSR 框架向内核 Q6 客户端广播 ADSP down/up（注：该内核栈属 Elite 启动分支，AR 分支不加载，[19.5 开头边界](../19_Kernel_Audio/19_19.5_QDSP6客户端与APR_VM传输.md)） | [19.5 §4](../19_Kernel_Audio/19_19.5_QDSP6客户端与APR_VM传输.md) |
| Android 用户态 PAL | Stream 收到错误后的重连/重建语义 | [15.6 ResourceManager](../15_PAL_Architecture/15_15.6_ResourceManager-PAL核心管理模块.md)（资源/会话重建） |

> **勘误式提醒**：18.2 已核验"SSR 清图（reset_only=1）"与"GVM 断连清 session（reset_only=0）"是**两件事**；场景化写作最常犯的错误是把两者并成一条"SSR 全清"路径。

## 4. 静音开机（Silent Boot）

产品级"开机不发声"的守护：`auto-audiod` 的 Silent Boot 监控在开机阶段监听内核静默模式节点并向 plugin 发送 SILENT_MODE 消息（[16.4 Silent Boot 监控](../16_Vendor_QNX_Architecture/16_16.4_Silent_Boot监控.md)；**实际拦截效果与是否编入产品未验证**——16.4 已明确"通知已送达"与"效果已发生"需分开对待，AR 主线 SILENT_BOOT_ENABLED 未定义时为 no-op）。它与 Framework 层的开机音（SystemUI/开机动画）是不同层的东西——16.4 已给出守护进程侧的证据链，本篇不重复。
