# 19.2 构建配置与模块清单：从 defconfig 到 audio_*.ko

> [← 上一个](19_19.1_内核音频通路总览.md) ｜ [本章导航](README.md) ｜ [下一个 →](19_19.3_ASoC声卡注册.md)

本产品内核音频模块的构建链条有**两个入口**，本树只有其中一个实际接线。本文逐项给出配置、Kbuild 对象与产品打包名的对应，并记录两处不能证明的环节。

## 1. 配置链条（本树实际路径）

```mermaid
flowchart LR
    BC[BoardConfig.mk:152<br/>KERNEL_DEFCONFIG := autogvm-qgki_defconfig] --> DF[arch/arm64/configs/vendor/autogvm_GKI.config<br/>:1 CONFIG_QTI_QUIN_GVM=y]
    DF --> TM[techpack/audio/Makefile:2-4<br/>ifeq CONFIG_QTI_QUIN_GVM → include gvmauto.conf]
    TM --> GC[config/gvmauto.conf<br/>14 个 CONFIG_...=m]
    GC --> KB[asoc|dsp|ipc|soc Kbuild<br/>各 _dlkm.o 模块]
    KB --> PK[msmnile_gvmq.mk:188-199<br/>AUDIO_DLKM 打包]
```

关键事实：

- `CONFIG_QTI_QUIN_GVM=y` 来自 defconfig 片段 `autogvm_GKI.config:1`（debug 变体 `autogvm-qgki-debug_defconfig` 由 `scripts/gki/generate_defconfig.sh` 在构建期生成，树内无此文件，其行号不可静态核对）；`autogvm_QGKI.config` 里没有 techpack 音频模块 CONFIG，仅有内核 ALSA 核心相关项（:26 `CONFIG_AUDIO_QGKI=y` 门控内核音频核心代码、:73 `CONFIG_SND_CTL_HASHTABLE=y`、:74 `CONFIG_DISABLE_SND_CTL_FIND_HOLE=y`），音频模块全部由 techpack 配置片段提供；
- techpack/audio/Makefile:2 用 `ifneq ($(CONFIG_ARCH_QTI_VM), y)` 包住目标选择，:3-4 在 `CONFIG_QTI_QUIN_GVM=y` 时引入 `config/gvmauto.conf`；
- `gvmauto.conf`（在 `ifeq ($(CONFIG_QGKI), y)` 内）导出的模块开关：

```make
// kernel/msm-5.4/techpack/audio/config/gvmauto.conf:4-19（逐字摘录）

export CONFIG_SND_SOC_GVM_AUTO_SPF=m
```

产品侧清单（`device/qcom/msmnile_gvmq/msmnile_gvmq.mk:188-199`）恰好是上表打包列的 10 个 `.ko`：

```make
// device/qcom/msmnile_gvmq/msmnile_gvmq.mk:188-198（逐字摘录；:199 的 PRODUCT_PACKAGES += $(AUDIO_DLKM) 未含）
#Audio DLKM
AUDIO_DLKM := audio_apr.ko
AUDIO_DLKM += audio_snd_event.ko
AUDIO_DLKM += audio_q6_notifier.ko
AUDIO_DLKM += audio_adsp_loader.ko
AUDIO_DLKM += audio_q6.ko
AUDIO_DLKM += audio_platform.ko
AUDIO_DLKM += audio_hdmi.ko
AUDIO_DLKM += audio_stub.ko
AUDIO_DLKM += audio_native.ko
AUDIO_DLKM += audio_machine_msmnile.ko
```

> **打包名与实际加载名的差异（如实声明）**：
> 1. Kbuild 产出的模块名是 `apr_dlkm.ko`/`q6_dlkm.ko`/`platform_dlkm.ko`/`machine_dlkm.ko`/`native_dlkm.ko` 等，而清单里的打包名是 `audio_apr.ko` 等；**把 `*_dlkm` 改名/包装成 `audio_*.ko` 的 Android 模块定义文件未在本树定位**（全树 grep `audio_machine_msmnile` 仅命中产品 mk 清单与其它目标的同类清单，如 `vendor/qcom/opensource/audio-hal/primary-hal/configs/msmnile/msmnile.mk:103-125` 的 `BOARD_VENDOR_KERNEL_MODULES` 列表，末项 `audio_machine_msmnile.ko` 在 :125）。上表对应关系按"CONFIG→Kbuild 对象→同位置打包名"推断，未由一份构建文件直接证明。
> 2. **产品实际按 `*_dlkm` 名加载模块**：`init.target.rc:37-39`（Elite 默认分支）以 `modprobe` 加载 `machine_dlkm`/`platform_dlkm`/`q6_dlkm`/`apr_dlkm` 等 19 个模块；`BoardConfig.mk:167` `BOARD_VENDOR_KERNEL_MODULES += $(shell ls $(KERNEL_MODULES_OUT)/*.ko)` 通配安装全部 .ko。
> 3. `spf_machine_dlkm.ko`（dummy machine，见 [19.3](19_19.3_ASoC声卡注册.md)）由 `CONFIG_SND_SOC_GVM_AUTO_SPF=m` 构建，**不在 `AUDIO_DLKM` 清单里**，但 **AudioReach 启动分支显式加载它**（`init.target.rc:42-45` 仅 modprobe `stub_dlkm spf_machine_dlkm`）。打包与加载的完整分支机制见 [19.6 §3](19_19.6_用户态消费与插件分发.md)。

## 3. 实际加载：init.target.rc 双分支

产品的模块加载由启动属性 `ro.boot.audio` 分支控制（`init.target.rc:36-45` 逐字摘录见 [19.6 §3](19_19.6_用户态消费与插件分发.md)）：

| 分支 | 加载的模块（modprobe 名） | 卡定义/HAL 属性 |
|---|---|---|
| Elite 默认（`ro.boot.audio=""`） | `snd_event/wglink/q6_pdr/q6_notifier/apr/adsp_loader/q6/native/usf/pinctrl_wcd/swr/platform/wcd_spi/stub/wcd_core/wsa881x/wcd9360/hdmi/machine` 19 个 `_dlkm` | `vendor.audio.card.def=card-defs-dummy.xml`（空定义） |
| AudioReach（`ro.boot.audio=audioreach`） | 仅 `stub_dlkm` + `spf_machine_dlkm` | `ro.hardware.audio.primary=msmnile.ar` |

即：**本表 §2 的 10 个打包模块全部属于 Elite 分支的内核栈**；AudioReach 分支的内核音频足迹只有 dummy 声卡 + stub codec，数据/控制面完全在用户态（AGM/GSL，[19.6](19_19.6_用户态消费与插件分发.md)）。实机取哪个分支由 bootloader 属性决定，静态不可证。

## 4. 第二个配置入口：sa8295gvmauto.conf（本树未接线）

`techpack/audio/config/sa8295gvmauto.conf` 是为 `CONFIG_SND_SOC_GVM_SA8295` 准备的外部模块构建配置（由 `ipc/Kbuild:17` 的 `CONFIG_SND_SOC_AUTO=y` 分支在 `:39` include，:178 还要求 `vendor/qcom/opensource/audio-kernel` 目录——该目录**不在本树**）。与 `gvmauto.conf` 的差异：

| 差异点 | gvmauto.conf（在树接线） | sa8295gvmauto.conf（未接线） |
|---|---|---|
| machine | `SND_SOC_GVM_AUTO_SPF`（dummy）+ `SND_SOC_SA8155` | 仅 `SND_SOC_SA8295`（Kbuild 同样映射到 sa8155.o，asoc/Kbuild:194-197） |
| 后处理 | `QTI_PP`、`SND_HWDEP_ROUTING` | `QTI_PP`、`SND_HWDEP_ROUTING` + `DTS_EAGLE`、`DOLBY_DS2`、`DOLBY_LICENSE` |
| VM 传输/FE | APRV2_VM、QDSP6V2_VM、QDSP6V2、SSR、ADSP_LOADER、NOTIFIER | 同左 |

> **勘误（负结论）**：`CONFIG_SND_SOC_AUTO`、`CONFIG_SND_SOC_GVM_SA8295` 在本树 defconfig 片段（`autogvm_QGKI.config`）中**零命中**，且 `vendor/qcom/opensource/audio-kernel` 目录不存在；因此 `sa8295gvmauto.conf` 及其 Dolby/DTS 开关在本产品构建中**未被证明生效**。不应把该文件的存在解读为"本产品内核启用 Dolby DS2/DTS Eagle"。

## 5. 检查清单（读懂一个模块是否真的在跑）

1. 它的 CONFIG 来自哪个 conf 片段？（在树路径 = `gvmauto.conf`）
2. 它映射到哪个 `*_dlkm` Kbuild 模块？
3. 它是否出现在 `msmnile_gvmq.mk` 的 `AUDIO_DLKM`？它属于哪个启动分支（`init.target.rc:36-45`）？
4. 运行态验证（`/proc/modules`、`/dev/snd/`）不在本库范围（静态知识库边界）。
