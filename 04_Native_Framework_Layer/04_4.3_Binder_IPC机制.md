## 4.3 Binder IPC机制 — 音频进程间通信

### 概述

Android音频系统的Binder IPC连接了App进程中的libaudioclient与audioserver进程中的AudioFlinger。控制命令（创建Track、start/stop、音量设置等）通过Binder传输，而音频数据本身通过共享内存传递，实现了控制面与数据面的分离。

**关键设计原则：**
- 控制命令走Binder IPC（低频、小数据量）
- 音频数据走共享内存（高频、大数据量）
- App进程与audioserver进程完全隔离

### 4.3.6 createTrack完整Binder交互时序

```mermaid
sequenceDiagram
    participant App as App进程
    participant AT as AudioTrack
    participant APS as AudioPolicyService
    participant AF as AudioFlinger
    participant Track as TrackHandle

    App->>AT: set() → createTrack_l()
    AT->>APS: getOutputForAttr(attrs)
    APS-->>AT: outputId + portId

    Note over AT,AF: === 第一次Binder调用: createTrack ===
    AT->>AF: createTrack(CreateTrackRequest)
    Note right of AF: 1. 根据outputId找到PlaybackThread<br>2. 分配共享内存(cblk+buffers)<br>3. 创建Track对象<br>4. 创建TrackHandle(BnAudioTrack)
    AF-->>AT: CreateTrackResponse<br>(IAudioTrack, outputId, frameCount, ...)

    Note over AT: 5. 映射cblk共享内存
    Note over AT: 6. 创建AudioTrackClientProxy
    Note over AT: 7. 如需回调，创建AudioTrackThread

    App->>AT: start()
    Note over AT,Track: === 第二次Binder调用: IAudioTrack.start() ===
    AT->>Track: IAudioTrack->start()
    Note right of Track: 8. Track加入PlaybackThread活跃列表<br>9. 唤醒混音线程
    Track-->>AT: OK
```

**createTrack()的Binder调用开销：**
- 一次Binder事务传输CreateTrackRequest
- 服务端分配共享内存，返回IAudioTrack Binder对象+共享内存fd
- 通过`mmap()`映射共享内存到App进程
- 后续数据传输不再经过Binder

### 4.3.8 Binder死亡通知与Track重建

当audioserver进程崩溃时，App进程中的Binder代理会收到死亡通知。AudioTrack通过`DeathNotifier`内部类处理此场景：

```mermaid
sequenceDiagram
    participant AF as AudioFlinger(崩溃)
    participant DN as DeathNotifier
    participant AT as AudioTrack
    participant AF2 as AudioFlinger(重启)

    AF->>DN: binderDied()
    DN->>AT: mProxy->binderDied() → 恢复/重建Track
    Note over AT: 如果mDoNotReconnect=false
    AT->>AT: restoreTrack_l()
    AT->>AF2: createTrack(CreateTrackRequest)
    AF2-->>AT: CreateTrackResponse
    Note over AT: 恢复音量/速率等参数
    AT->>AF2: IAudioTrack->start()
```

**两种处理策略：**
1. **自动重建**（`mDoNotReconnect=false`）：`restoreTrack_l()`自动重连
2. **通知应用**（`mDoNotReconnect=true`）：回调`EVENT_NEW_IAUDIOTRACK`，让应用自行处理

### 4.3.10 Binder线程模型

#### audioserver端Binder线程池

audioserver进程的Binder线程池按Binder驱动默认策略管理（本树 audioserver 源码无 `setThreadPoolMaxThreadCount()` 调用，grep 无匹配；"默认16"无源码依据，实际线程数由驱动按并发负载动态决定）。

#### 关键Binder调用频率（经验参考，非源码结论）

| 方法 | 典型频率 | 耗时 | 说明 |
|------|---------|------|------|
| `createTrack()` | 每个Track创建一次 | 经验~5ms量级 | 含共享内存分配 |
| `start()/stop()` | 播放状态切换 | 亚毫秒量级 | 简单状态变更 |
| `setVolume()` | 音量变化时 | 0（不走Binder） | 写入cblk.mVolumeLR |
| `getTimestamp()` | 按需/周期 | 亚毫秒量级 | 读取服务端位置 |
| `createAudioPatch()` | 路由变化时 | 毫秒~十毫秒量级 | 涉及HAL配置 |
| `openOutput()` | 设备热插拔 | 十毫秒~百毫秒量级 | HAL流打开 |

> 注：上表耗时列为**经验数量级参考**（无本树源码/实测依据），精确值取决于HAL与负载；频率列为典型使用模式。

#### Binder调用优化

1. **音量通过共享内存传递**：`setVolume()`实际写入`cblk.mVolumeLR`，而非每次Binder调用
2. **播放速率通过队列传递**：`setPlaybackRate()`写入`cblk.mPlaybackRateQueue`
3. **flush/stop通过原子变量**：通过`mFlush`/`mStop`计数器传递给服务端

### 4.3.11 IAudioPolicyService Binder接口

[`IAudioPolicyService`](frameworks/av/media/libaudioclient/aidl/android/media/IAudioPolicyService.aidl) 是音频策略决策服务（**本树12L已是AIDL**，无 `include/media/IAudioPolicyService.h`），与AudioFlinger分离：

**核心方法：**

| 方法 | 说明 |
|------|------|
| `getOutputForAttr()` | 根据音频属性获取输出路由 |
| `getInputForAttr()` | 根据音频属性获取输入路由 |
| `setDeviceConnectionState()` | 设备连接状态变更 |
| `setPhoneState()` | 设置通话模式 |
| `setForceUse()/getForceUse()` | 强制使用配置 |
| `setVolumeIndexForAttributes()` | 按属性设置音量 |
| `createAudioPatch()/releaseAudioPatch()` | 策略层路由Patch |
| `registerClient()` | 注册IAudioPolicyServiceClient |

> **负结论**：`getAudioPolicyConfig()` 不在本树 IAudioPolicyService.aidl（grep 无匹配）。

**与IAudioFlinger的分工：**
- `IAudioPolicyService`：决定"怎么路由"（策略决策）
- `IAudioFlinger`：执行"怎么混音"（策略执行）

### 4.3.12 Binder IPC数据流总结

```mermaid
graph LR
    subgraph 控制面["控制面 (Binder IPC)"]
        C1["createTrack/createRecord"]
        C2["start/stop/pause/flush"]
        C3["setVolume/setPlaybackRate"]
        C4["createAudioPatch"]
        C5["openOutput/openInput"]
    end

    subgraph 数据面["数据面 (共享内存)"]
        D1["PCM音频数据"]
        D2["cblk控制块"]
        D3["音量/速率参数"]
        D4["flush/stop标志"]
    end

    C1 -->|"一次Binder调用<br>建立共享内存"| D1
    C3 -->|"首次Binder<br>后续写入cblk"| D3
```

**零拷贝数据路径：**
1. App通过`obtainBuffer()`获取共享内存中的可写区域
2. App直接`memcpy()`写入PCM数据
3. App通过`releaseBuffer()`更新`mFront`指针
4. AudioFlinger混音线程直接从共享内存读取数据
5. 整个数据传输路径无Binder调用、无额外拷贝
